MediQueue Database Update

Ahmed Ali Al Jader · 3 November 2026 · CSC 305

The MySQL database for the kiosk booking prototype is designed, tested, and ready for the Java team to connect to. It follows the scope in our SRS (26 Oct): identify the patient, pick a clinic, view open times, and book one.

What's done

  • Schema with 4 tables and 2 views, built for MySQL 8.0.
  • Double-booking protection enforced by the database itself, safe when several kiosks book at the same moment (FR-08, NFR-03).
  • Simulated test data: patients, clinics, and two weeks of appointment slots (NFR-06).
  • A limited database account for the kiosk app that can read and book but cannot edit or delete records (NFR-05, NFR-07).
  • Ready-made queries for every SRS function, so the DAO layer can use them directly.

Files are in the database/ folder: schema.sql, seed.sql, and README.md.

Views

  • available_slot: future, unbooked times at active clinics. This is what the kiosk lists (FR-05). An empty result means "no times available" (FR-10).
  • booking_confirmation: everything the confirmation screen shows, including a reference number like MQ-000042 (FR-09).

How double booking is prevented

A unique index on the appointment table allows only one active booking per slot. If two kiosks try to book the same time, MySQL accepts the first and rejects the second with error 1062. The app catches that error and shows "this time is no longer available, please choose another" (FR-11).

For the Java team: don't check availability with a SELECT and then INSERT. Two kiosks can both pass the check before either one saves. Just run the INSERT and handle error 1062.

Cancelled bookings stay in the table for history, and the slot becomes bookable again.

Set it up on your laptop

  1. Install and start MySQL 8.0.
  2. From the database/ folder, run:
mysql -u root -p < schema.sql
mysql -u root -p < seed.sql

Running schema.sql deletes and rebuilds the whole mediqueue database. Use it to reset test data, not on data you want to keep.

Slots are created for the 14 days after you load the data, so reload before a demo to keep the times in the future.

Queries for the DAO layer

-- FR-01  Identify the patient
SELECT patient_id, full_name FROM patient WHERE national_id = ?;

-- FR-03  List clinics
SELECT clinic_id, name, location FROM clinic
WHERE is_active = TRUE ORDER BY name;

-- FR-05  Open times for a clinic (empty result -> FR-10 message)
SELECT slot_id, start_time, end_time FROM available_slot
WHERE clinic_id = ? ORDER BY start_time;

-- FR-07  Book (error 1062 -> FR-11 message)
INSERT INTO appointment (slot_id, patient_id) VALUES (?, ?);

-- FR-09  Confirmation screen
SELECT * FROM booking_confirmation WHERE appointment_id = ?;

The README has a full JDBC book() method that returns the new appointment ID and handles error 1062.
